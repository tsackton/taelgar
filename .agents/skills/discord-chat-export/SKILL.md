# Discord Chat Export

Preserve the two-person Taelgar conversation as a development source, not canon. Follow the vault `AGENTS.md`. The established destination is `Worldbuilding/Chats and Emails/Chats`; existing notes are evidence of prior work, not proof that their dates are completely or correctly exported. Do not replace an existing note during a re-export without a scoped preview and approval.

For another user-approved channel, confirm its channel ID, participants, campaign relevance, and destination independently. Keep its raw staging and checkpoint separate from the Tim–Mike DM. A deleted Discord account may need a user-supplied identity mapping; retain the source label in message lines and document the mapping in the note.

## Source and credentials

- Inspect the current exporter before use. The known local checkout is `D:\personal\taelgar-utils`; `cli/discord-export.py` calls `src/taelgar_utils/utilities/discord_export.py` and DiscordChatExporter. Its core config is `configs/core/discord_export_config.yaml`. Check its current channel ID against the intended DM. The checked-in executable path is for macOS, so supply the actual local executable path in a temporary config on Windows. Never assume a changed checkout still has the behavior described here.
- The live exporter reads `DISCORD_USER` from the process environment or `.env` and passes it to a current DiscordChatExporter CLI as `DISCORD_TOKEN` in the child process environment. Treat it as a secret: never request it in chat, inspect or print its value, put it in a command argument, write it to the vault, commit it, or include it in logs. Verify that the local wrapper still keeps it out of the assembled command before a live run. Let the user supply the credential locally. Do not fetch a token from browser storage or network traffic.
- Discord says automation of ordinary user accounts outside its bot/OAuth API is forbidden and may lead to account termination. Explain that risk before the first live export and let the user choose whether to run the existing tool. Discord's official data package is an alternative source, but it contains only messages sent by the requesting account; it cannot alone reconstruct both sides of this DM. A user-supplied JSON export can enter the processing workflow without live access.
- Keep raw JSON and downloaded media in a user-chosen private staging directory outside the vault. The raw DM includes off-topic private material. Do not commit it or copy all media into the vault. The utility's `--reprocess-only --force` mode can produce day-split raw Markdown from an existing JSON export. Use `--force` only on disposable staging output; incremental append can duplicate messages.

## Choose dates and prepare the run

If absent, choose the first day with the user: the archive index says “current through June 03 2026,” but that is only a clue, especially for a re-export. Initialize once; do not silently infer completeness from filenames or reset a checkpoint.

- Process calendar days in order, including days with no Taelgar material. Stop at yesterday in the checkpoint timezone so a day is complete. A run may fetch several days at once, but review and checkpoint them one at a time.
- For an incremental fetch, derive `last_retrieved_date` in a temporary config from the checkpoint, with at least the last completed day as overlap. Do not edit the tracked core config to maintain the cursor. The exporter uses `--after`; verify the resulting JSON's first and last timestamps and do not rely on an unverified inclusive/exclusive boundary. For a deliberate re-export, fetch the requested full range and use a separate checkpoint rather than overwriting the current one.
- Run the exporter with its `--config` and `--output` options, using an output path in staging. Require a successful process exit and a parseable JSON `messages` array (the current DiscordChatExporter output uses lowercase keys). Its current converter may warn yet leave a successful process status, so independently verify the JSON and day inventory before treating a run as complete. Keep source IDs and timestamps available for comparison.

## Review one day at a time

- Group by message timestamp converted to `America/New_York`, in source order. Compare each day's raw JSON to any generated Markdown; account for every message and attachment. Do not silently drop records with missing or invalid timestamps: stop and report them.
- If the user asks for a complete channel archive, retain every message, including unrelated exchanges, attachment-only posts, and call records. Keep all source attachments linked from those messages. The relevance filter below applies only to curated exports.
- Keep substantive Taelgar worldbuilding, character background, roleplay scenes, campaign setting and adventure design, and short adjacent replies needed to understand them. Exclude vault organization and coding even when they concern Taelgar: folder layouts, naming conventions, metadata schemas, templates, queries, header rendering, publication filters, source-import workflows, website builds, and debugging. Omit unrelated personal or logistical conversation. In mixed days, retain the substantive discussion and its needed context while omitting tooling exchanges. Decide from conversational purpose, not titles, fantasy names, or keywords alone. Preserve sender, time, sequence, wording, uncertainty, and disagreements; do not rewrite brainstorming as settled lore.
- Retain species-level mechanics as setting development, including elf stat blocks, dwarf runes and blessings, other species traits, and their design and balance discussions. References to individual PCs as playtest examples do not turn species design into character-build optimization. Omit individual character mechanics, rebuilding, and optimization unless they also develop retained character background or spell-source flavor; continue to omit coding, publishing, and storage logistics around species rules.
- A lore quotation, pasted vault passage, screenshot, or sample NPC record used to demonstrate an organization or coding problem does not by itself make an exchange relevant. Retain discussion that actually develops, questions, revises, or interprets the lore or scene; the quoted material alone may be an existing source example. Inspect the introduction and replies to distinguish these uses. A short reply such as “yes” needs enough preceding context to establish what was agreed.
- Ask the user when a tooling exchange contains apparent lore but its role as a quotation/example versus substantive discussion is unclear, or when only a small naming or lore decision would justify keeping an otherwise tooling-only day. Show the passage and a brief proposed keep/omit decision; batch independent questions when practical. Keep that day pending without writing its final note or advancing its checkpoint until the user resolves the ambiguity. Continue independent review of later days, but do not advance past a pending day.

## Advance and verify

- Advance the checkpoint only after the entire day has been reviewed, the note and relevant assets have been verified, or the day has been confirmed to contain no Taelgar content. Record source and retained message counts. `export_state.py advance` rejects gaps and duplicate advances. The export process finish time is never the checkpoint.
- Re-read each changed note in full. Check YAML, tags, links, attribution, timestamp order, attachment paths, the complete scoped diff, and `git diff --check`. Preserve unrelated work. Report processed date range, notes written, skipped days, counts, unresolved source gaps, and the new last completed day. Do not claim complete coverage when a source day was missing or filtering was uncertain.
